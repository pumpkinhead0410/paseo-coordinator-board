# 보드 배정 작업자의 첫 턴 알림

**추천은 보드의 키 기반 세션 생성 경로를 유지하고, Paseo가 첫 프롬프트와 함께 완료 구독을 받을 수 있도록 SDK·데몬을 확장하는 것입니다.** 현재 설치된 0.17.4에서는 배정 뒤에 옵션 하나를 붙여 같은 효과를 낼 수 없습니다. MCP 생성은 알림을 제공하지만 배정 재시도의 키를 받지 않고, 생성 후 별도로 보내는 MCP 프롬프트는 응답 유실 후 같은 작업을 두 번 보낼 수 있습니다.

이 연구의 대상은 같은 호스트에서 사람이 위임한 **첫 작업 한 건**입니다. 권한 요청 한 건과 그 뒤의 턴 종료는 각각 알릴 사건입니다. 후속 작업은 그 프롬프트를 보낸 호출자의 기존 구독을 따릅니다. 부모가 바쁘면 현재 턴이 끝난 뒤 읽을 수 있어야 합니다. 수신 큐 등록, 모델에 디스패치, 부모의 답변 완료는 각각 다른 시점입니다. 아래의 횟수에는 측정 지점을 표시했습니다.

## 현재 계약과 관찰 근거

- **보드** — 코디네이터 소유권과 관리 세션 범위를 검사하고, 작업 위치·확정 경로·권한 모드를 재검사합니다. 요청 키에서 작업자 ID와 첫 메시지 ID를 만들고, 생성 키·부모·보고 메타데이터·스킬 시스템 프롬프트를 함께 전달합니다. 같은 키의 응답을 잃으면 원래 생성 요청을 재생합니다. 제품 코드에서 배정 함수의 직접 호출자는 assign_board_worker입니다. 일반 SDK 세션 생성의 기본값은 별도로 보존해야 합니다. [배정 도구](../../server/operations.ts#L229) · [배정과 재시도](../../server/dispatch.ts#L156) · [배정 시험](../../test/dispatch.test.ts#L213)
- **사건 기록** — 기존 조사 커밋에서 작업자 `f1f04e98`의 배정 턴에는 완료 알림이 관찰되지 않았고 같은 작업자에게 후속 프롬프트를 보낸 뒤에는 관찰됐습니다. 상시 자동화 이전에는 G로 결과를 보내고 F의 `read_board_conversation`으로 현재 상태를 확인할 수 있습니다. 별도 브랜치의 원본은 `git show 3591a4d:docs/design/coordinator-worker-status.md`의 ‘완료 신호가 없었던 경로’ 절입니다. 이번 실행은 그 사건의 대화 재연이 아니라 설치 코드에서 두 경로를 대조한 것입니다.
- **설치본** — 기준은 보드 `32a744c`·0.5.24, 설치된 Paseo 서버 0.17.4입니다. 저장소의 개발 SDK는 0.16.2이며 지원 하한도 0.16.2입니다. 새 기능에 호스트의 명시적 지원 표시가 필요합니다. 설치본 소스 위치는 CLI의 `node_modules/@getpaseo` 아래이며, 아래에서 서버 경로는 `server/dist/server/server/`를 생략합니다. [개발 의존성](../../package.json) · [호스트 지원 범위](../../paseo-plugin.json)

**비용의 단위**는 부모에게 들어가는 메시지입니다. 권한 요청이 n개이고 종료가 한 번이면 정상 목표는 n+1건입니다. Paseo가 대기 메시지를 합칠 수 있어 모델 턴 수와 메시지 수는 다릅니다. 별도 실험에서 바쁜 부모에게 큐 알림 뒤 명시적 steer를 보내자 두 메시지가 하나의 idleOnly=false 배치로 전달됐습니다. 알림 자체가 현재 턴을 깨우지 않는 것과 후속 긴급 전송에도 절대 합류하지 않는 것은 다른 보장입니다. 토큰·요금과 공급자별 배치 횟수는 측정하지 않았습니다.

| 업스트림 가설 | 설치 파일을 읽어 메모리 안에서 **등록 조건에 session도 포함**하고 같은 함수에 호출자·구독 의존성을 공급했습니다. 고정 작업자 ID·메타데이터 → 등록 → 고정 ID의 첫 프롬프트 → 확정을 확인했습니다. 실제 설치의 세션 호출자는 의존성을 주입하지 않으며 wire 스키마는 알림 옵션을 버립니다. 이 실험은 결합 지점만 검증합니다. |

**공개 인터페이스에서 막히는 지점**

- **B·C의 호출 권한** — 플러그인 RPC의 `PluginHandlerContext`가 제공하는 실행 인터페이스는 `paseo: PaseoApi`입니다. 다른 MCP 도구를 코디네이터 신원으로 호출하는 공개 메서드는 여기에 없습니다. 코디네이터 모델에 두 번째 도구 호출을 맡기면 모델이 배정 경로·모드·지시문을 다시 구성해야 하고 보드의 최종 검증과 실행 사이에 간격이 생깁니다. MCP 생성은 라벨·settings를 받지만 보드가 쓰는 임의 metadata·systemPrompt·고정 요청 키 묶음을 제공하지 않습니다. 출처는 `plugin/dist/server/contracts.d.ts:9`와 `agent/tools/paseo-tools.js:840–890`입니다.
- **D의 배달 영수증** — 출처 있는 SDK 메시지는 `agent-message`로 큐에 들어갑니다. 네이티브의 `agent-notification` 종류·권한 알림 표시까지 복제하려면 프로토콜 지원이 필요합니다. 0.17.4 세션 전송은 디스크에 pending을 기록하고 메모리 큐에 넣은 뒤, 실제 디스패치 전에 accepted 응답을 줄 수 있습니다. 이때 데몬이 종료되면 큐를 잃을 수 있고 같은 키 재시도는 outcome_unknown으로 멈춥니다. 다른 키를 발행하면 먼저 수신한 경우와 구별할 수 없습니다. 보드만으로 구현한다면 원장과 수신 타임라인 대조, 불명확 표시가 필요합니다. 훅→SDK 실험은 DaemonClient를 대역으로 연결했으며 호스트 기능 분기는 별도로 실행했습니다. 또한 같은 큐의 정상 close()에서는 바쁜 부모의 대기 건도 idleOnly=false·steer·unarchive=true로 배출됐습니다. 비정상 종료로 메모리 큐를 잃는 경우와 구분해야 합니다. D에는 턴 종료가 발행되지 않은 작업자 close/archive 훅도 필요합니다. 기존 SDK에는 이미 큐에 든 건을 보드 관리 해제와 함께 철회하는 공개 핸들이 없습니다. 근거는 `session.js:7009–7074`, `agent/agent-messages/delivery.js:58–66`, `message-receipts/index.js:31–58`입니다.

**네이티브 경로의 한계.** 등록의 영속화와 관찰 시작은 다릅니다. pending 등록은 dispatch 결정 뒤 관찰을 엽니다. 매우 짧은 턴은 초기 조회로 마지막 idle 상태를 회수할 수 있지만 이미 해결된 권한이나 다음 턴으로 바뀐 결과를 고유 사건으로 복원한다는 보장은 없습니다. 특히 관찰을 열기 전에 취소가 끝나서 host.wait()가 idle만 반환하는 경우, 실제 openFinishObservation 결과에는 취소 이유가 없고 기본 finished로 분류됩니다. 취소 사건 자체가 버퍼에 들어온 경우에만 was canceled가 보존됩니다. 저장된 구독에는 caller·child·server와 소유권 조건만 있고 turnId·권한별 배달 기록·pending/accepted 구분이 없습니다. 등록 직후 accept 없이 재기동한 실험에서 초기 idle 결과를 주자 디스패치 확인 없이 finished 1건을 보냈습니다. 재시작 시 같은 쌍의 등록을 모아 재개하고, 실행 중 새 등록이 accept되면 앞 등록을 대체합니다. 같은 부모·작업자의 pending 등록 두 개를 순서대로 확정하고 단일 종료를 공급해 enqueue 1건을 확인했습니다. 같은 쌍의 프롬프트마다 별도 완료 1건을 보장하는 모델로 해석하면 안 됩니다. 근거는 `agent/finish-subscriptions/internal/{json-store,observation,observation-stream}.js`, `agent/finish-subscriptions/index.js:149–157,245–307`입니다.

## 추천 계약과 수용 기준

**Paseo 유지관리자에게 제안할 변경**은 기존 키 기반 create에 명시적 첫 턴 알림과 기능 협상을 추가하는 것입니다. 실제 호출 주체·배정 관계를 검증하고, 생성 영수증에 알림 의도와 확정 결과를 함께 묶습니다. 첫 프롬프트가 거절되면 구독을 취소해야 합니다. 현행 session은 첫 턴 실패를 반환값으로 돌려주는 분기가 있어, 등록 조건만 넓힌 실험본에서는 시작 거절을 주입하자 initialPromptStarted=false인데도 accept가 실제 호출됐습니다. 현행 session.js는 생성 함수가 돌려준 initialPromptError를 꺼내지 않으며 CreationService는 prompt_started를 건너뛰고 completed 영수증을 기록할 수 있습니다. SDK도 오류나 세션 부재만 검사하므로 보드에 성공처럼 보일 수 있습니다. 첫 프롬프트 거절 원인과 미시작 상태를 생성 응답·영수증에 노출해야 합니다(`session.js:3667–3691`, `creation/index.js:127–142`). 부모가 바쁘거나 재시작할 때는 사건별 고정 ID와 영속 수신 영수증이 필요합니다. 배달 결과가 불명확하면 같은 작업 재전송을 보류하고 해당 사건을 조회할 수 있게 합니다.

**보드 유지관리자에게 제안할 변경**은 기존 요청 키·배정자·라우팅·작업 권한을 보존하고 지원 호스트에서만 구독 의도를 보내는 것입니다. 원래 부모가 교체되거나 프로젝트가 관리 해제되면 대기 알림을 취소하고 새 부모는 명시적으로 상태를 조회하는 정책을 추천합니다. 이미 큐에 든 메시지까지 막으려면 enqueue 직전 검사와 실제 dispatch 직전 취소·재검사가 모두 필요합니다. 부모 라벨이 남아 있으면 현행 네이티브 소유권 검사만으로 이 정책을 충족할 수 없습니다. 특히 D의 SDK send는 0.17.4 세션 요청에 unarchive=false를 실어 보내지 않습니다. 데몬 큐가 이 값을 생략한 메시지 배치를 보관 해제 가능한 것으로 처리하므로 배정 뒤 부모 보관에 대한 별도 보호가 필요합니다(`session.js:7009–7031`, `agent/agent-messages/delivery.js:95`, `websocket-server.js:390`). 기존 호스트에서는 배정 결과에 첫 턴 알림 미지원을 표시하고 F를 사용합니다.

다음은 구현 브랜치에서 확인할 **수용 기준 제안**입니다. 시험 호스트의 작업자 타임라인과 부모 큐·타임라인에서 요청 키, 첫 메시지 ID, 작업자·부모 ID, turnId, 권한 ID, 사건 키, enqueue·dispatch 시각과 실제 모델 턴을 대조합니다.

1. 같은 요청의 동시 호출·응답 유실·재시작 후 재시도 모두 작업자 1개, 첫 작업 1회, 같은 사건당 수신 1건입니다. 같은 키에 다른 내용은 거절합니다. 일반 생성·빈 프롬프트·알림 끔·기존 호스트에서는 암묵적 알림이 없어야 합니다.
2. 즉시 종료, 오류, 취소는 각각 실제 결과에 맞는 종료 신호 1건입니다. 시작 전 실패와 작업 시작 뒤 실패를 구분합니다. 같은 권한을 반복 관찰해도 요청 ID당 1건, 다른 요청은 각각 1건이며 해결 뒤 종료 1건이 도착해야 합니다.
3. 부모 실행·부모 권한 대기 중에 알림 단독으로 중단·steer·권한 자동 해제를 일으키지 않아야 합니다. 뒤이어 명시적인 긴급 전송이 들어오면 기존 배치 동작을 별도로 대조합니다. 해제 후 순서와 출처를 보존하고, 병합된 모델 입력 안에서도 사건별 메시지를 구분할 수 있어야 합니다.
4. 등록 전후, 첫 턴 수락 전후, enqueue 전후, dispatch 뒤 영수증 기록 전에 각각 프로세스를 종료해 재기동합니다. 유실·오배달·중복은 0건이 목표입니다. 불명확한 상태를 노출하는 복구 모드는 ‘정확히 1회’ 통과와 별도로 보고합니다.
5. 부모 교체·보관·분리, 프로젝트 관리 해제, 큐에 든 뒤의 변경을 각각 검사합니다. 권한 없는 호출·작업 위치·모드 변경을 거부하고 보드 메타데이터와 스킬을 유지합니다. 후속 send 구독이 겹치면 첫 턴과 다음 턴을 오인하거나 같은 사건으로 부모를 두 번 깨우지 않아야 합니다. 구독을 계속 유지하는 훅은 사용하지 않습니다.
6. 실제 같은 호스트에서 보드 배정과 일반 MCP send를 대조하고, 지원 하한과 기능 지원 버전에서 결과를 분리합니다. 제공자별 짧은 턴, 권한과 종료, 부모 모델 추가 턴·토큰 수를 실측합니다.

**사람이 정할 사항**은 업스트림 지원까지 F와 필요 시 G를 사용할지, 단기 D 구현에 비용을 쓸지와 관리 해제 때 이미 대기 중인 알림의 처리입니다. 사건별 정확히 1회가 필수라면 기존 네이티브 동작을 그대로 복사하는 것만으로는 수용 기준 4를 충족했다고 판정할 수 없습니다.
