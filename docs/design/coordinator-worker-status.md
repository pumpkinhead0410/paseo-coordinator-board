# 코디네이터의 작업자 상태 오보고 원인과 재발 방지 설계

**제안** — 코디네이터가 현재 상태를 답할 때 해당 세션의 상태를 그 턴에서 읽고, 결과나 결정 대기까지 말할 때는 마지막 발화도 확인한다. 다른 작업의 소식에 근거 없는 진행 문장을 덧붙이는 관행부터 없앤다. 사람이 요청하지 않아도 완료 즉시 알려야 하는지는 별도 제품 결정이다.

### 완료 신호가 없었던 경로

1. `assign_board_worker`는 관리 범위를 확인하고 `dispatchWorker`를 호출한다. 배정은 같은 요청 키에서 세션 ID와 첫 메시지 ID를 재사용한다. SDK의 `workspace.agents.create`에 부모, 첫 프롬프트, 보드 보고 메타데이터를 함께 넘긴다. 반환값은 배정한 세션·경로·모드 정보다. [operations.ts 229–245](../../server/operations.ts#L229) · [dispatch.ts 156–192, 208–228](../../server/dispatch.ts#L156)
2. 보드가 부모를 문자열로 넘기면 SDK는 이를 호출자 ID로 변환한다. 데몬은 이 호출자가 포함된 세션 생성 요청에서 관계를 해석하고 라벨을 넘긴다. 데몬 공통 생성 함수는 `kind === "mcp"`, 알림 활성화, 호출자 ID, 첫 프롬프트가 모두 있을 때만 첫 턴 **전**에 완료 구독을 등록한다. 세션 생성 경로는 첫 조건에서 빠진다. 사건 스냅샷 710행에서도 부모 라벨과 보고 메타데이터를 확인했다. 설치 패키지 근거는 `client/dist/index.js:33–58,100,279,545–553`, `client/dist/daemon-client.js:2071–2088`, `server/dist/server/server/session.js:3443,3657–3691`, 같은 디렉터리의 `agent/create-agent/intent.js:13–20`, `agent/create-agent/create.js:32–63`이다.
3. `coordinator-board/reports`는 대화용으로 연 작업자에게 `report_to_board`를 붙이는 스위치다. 호출하면 그 세션의 카드에 질문·검토 메모를 쓰며, 사람의 기존 메모와 충돌하면 거부한다. 이 경로에는 부모에게 메시지를 보내는 단계가 없다. 기존 턴·권한 훅도 대기 중인 카드 답장과 병합 알림을 재개한다. [reporting.ts 11–40](../../server/reporting.ts#L11) · [index.server.ts 197–214](../../index.server.ts#L197)
4. 대조군인 에이전트 간 `send_agent_prompt`는 호출자 ID가 있으면 기본으로 구독을 등록한다. 디스패치가 성립하면 구독을 확정하고, 관찰한 권한 요청·종료 등은 해당 호출자에게 큐로 보낸다. 바쁜 호출자에게는 지연될 수 있다. 설치 근거는 `agent/tools/paseo-tools.js:1444–1489`, `agent/finish-subscriptions/index.js:95–153`이다. 따라서 이번 배정 경로 자체에 첫 턴 구독 등록이 없다는 점까지 확인할 수 있다. 당시 구독 저장소의 과거 내용이나 개별 패킷 유실 여부는 대화 기록으로 복원할 수 없다.

**분기 검증** — 설치된 0.17.4의 실제 함수 `createAgentCommand`에 메모리 내 작업자 실행기와 구독 기록기를 연결했다. 부모·첫 프롬프트·보고 플래그를 주고 양쪽 모두 알림을 요청했다. 세션 생성은 첫 턴 1회·구독 0회였고, MCP 생성은 구독 등록 → 첫 턴 → 구독 확정 순이었다. 이 검증은 생성 함수의 등록 조건을 검사한다. 실제 메시지 배달 근거는 위 대화의 503·602행이다.

### 조회 없이 단정한 이유

**직접 확인** — 담당 ID는 맞았다. 잘못된 값은 두 답변에 재사용한 “계속 진행 중”이었다. 741행에서 코디네이터 본인도 직접 확인하지 않았다고 밝혔다. 전역 규칙 `~/.claude/rules/read-records-before-status-claim.md:4–5`는 상태 보고 전 기록 재확인을 요구한다. 보드 헌장도 관리 목록과 최근 발췌를 읽고 도착한 보고를 분류하라고 한다. 이미 수행 가능한 조회를 생략한 것이 오보고의 직접 원인이다. [lifecycle.ts 34–43](../../server/lifecycle.ts#L34)

**기여했을 가능성** — 두 도구 모두 작업자를 실행하지만, 일반 프롬프트의 알림과 보드 도구 설명의 “배정” 사이에는 부모가 무엇을 기다릴 수 있는지 차이가 있다. 배정 설명은 재시도·권한 조건을 밝히지만 첫 턴 구독 여부를 말하지 않는다. 헌장의 “도착한 보고”는 도착하지 않은 경우의 행동을 지정하지 않는다. 다른 세션의 실제 알림과 494행의 약속은 코디네이터가 같은 신호를 기대했다는 해석에 부합한다. 모델이 어느 문구 때문에 판단했는지는 확인할 수 없다. 구독이 있는 경우에도 알림 부재만으로 현재 상태를 판단할 수 없다.

## 대안과 책임

| 선택 | 효과 | 실패 모드와 유지 비용 |
|---|---|---|
| 부수적인 진행 문장 삭제 | 이번 두 답변에서 확인되지 않은 주장 자체를 제거한다. 실행 비용이 없다. | 사용자가 직접 상태를 묻는 경우에는 조회가 필요하다. |
| 기존 조회 + 코디네이터 지침·배정 설명 보강 **(추천)** | 한 번의 목록 조회로 여러 대상의 상태를 확인하고, 필요한 대상만 발췌한다. 알림 유무에 관계없이 작동한다. | 자유 문장의 준수는 모델에 의존한다. 보드 유지관리자가 지침과 행동 회귀 사례를 관리한다. 생성 시 헌장을 받은 기존 세션, 별도 지정된 코디네이터에도 적용되는 도구 설명과 실제 도구 노출을 시험해야 한다. |
| 상태 보고를 제품에서 강제 | 구조화한 보드 상태 출력은 읽기 성공 시에만 현재값을 표시할 수 있다. | 보드 밖 자유 답변까지 통제하려면 제공자별 출력 경로 개입이 필요하다. 문자열 검사로는 한국어 변형·인용·과거 시점을 오차단한다. 보드 화면에서만 강제하면 이번 대화는 그대로 통과한다. |

## 추천안의 호출 계약

보드 유지관리자는 헌장의 상태 보고 문장과 `assign_board_worker`의 도구 설명에서 배정 영수증의 의미를 명시한다. 일반 세션 생성으로 우회하거나 구독을 얻으려고 첫 프롬프트를 다시 보내면 배정·권한 검증 또는 한 번 실행 계약을 깨뜨릴 수 있다. 상태 저장소나 주기적 폴링은 추가할 필요가 없다. 새 헌장은 코디네이터 생성 시 설정된다. 이미 지정한 세션에는 기존 운영 예시에도 같은 사용법을 연결하고, 다음 대화용 열기에서 갱신되는 조회·배정 도구 설명으로 안내한다. 진행 중인 턴을 강제로 다시 열거나 기존 시스템 프롬프트를 덮어쓰지 않는다. [lifecycle.ts 164–175](../../server/lifecycle.ts#L164) · [coordinator.ts 74–79](../../server/coordinator.ts#L74) · [기존 세션 운영 예시](../../templates/coordinator-session.md)

- 다른 작업을 보고할 때 대상의 현재 상태가 필요 없으면 그 문장을 생략한다.
- 현재 상태를 묻거나 자발적으로 언급할 때는 **같은 응답 턴**에 `read_board_conversation({})`으로 관리 목록을 읽고 대상 ID·프로젝트를 대조한다. `status`와 `activityAt`은 호스트 상태와 그 갱신 시각이다. 조회 시각과 구분한다. 목록은 권한 요청이나 활성 턴을 반환하지 않는다. “실제로 작업 중인가, 응답을 기다리나”처럼 둘을 구분해야 하는 질문에는 목록에서 관리 범위를 확인한 ID로 `get_agent_status`를 반드시 읽고 보류된 권한 요청을 우선한다. 상세 조회가 실패하면 목록에서 읽은 원시 상태까지만 인용한다. [coordinator.ts 23–51](../../server/coordinator.ts#L23) · [discovery.ts 29–50, 72–85](../../server/discovery.ts#L29)
- 업무 결과나 대기 사유를 말하려면 `read_board_conversation({sessionId})`의 최근 발화와 시각을 확인한다. `idle`만 있으면 “조회 시점에 세션 대기”, 이 사건처럼 근거가 있으면 “세션은 대기 중이고 마지막 보고에서 통합 결정을 요청했습니다”라고 답한다. 검증·병합 승인에는 각각의 기존 절차가 적용된다.
- 조회 실패·목록 누락·범위 변경이면 현재 상태는 미확인으로 둔다. 발췌만 비어 있으면 확인한 실행 상태까지만 전달한다. 목록과 발췌 사이에 재개 등 모순이 보이면 상태를 다시 읽고 관측 시각을 붙인다. 판단을 카드에 남길 때 기존 `evidenceId` 검사를 재사용한다. [conversation.ts 131–142](../../server/conversation.ts#L131) · [coordinator.ts 54–71](../../server/coordinator.ts#L54)

## 구현 시 수용 기준

| 시험 | 통과 조건 |
|---|---|
| 원 사건 재생 | 보드 배정 뒤 A가 통합 대기로 바뀌고 B의 권한·완료 알림만 도착하게 한다. B를 보고하는 두 응답 모두 A에 대한 현재형 단정이 없거나, 그 응답에서 A를 읽고 관측 결과를 정확히 전달한다. |
| 직접 질문과 혼동 | 같은 제목의 두 세션을 두고 하나의 상태를 묻는다. 해당 ID의 실행 상태와 마지막 결과를 구분한다. 이전 턴의 조회, B 알림, 배정 영수증만 주어진 상태에서 A를 진행·완료로 단정하면 실패다. |
| 불완전하거나 바뀐 근거 | 접근 해제·조회 오류·빈 발췌·idle 직후 재개·권한 요청을 각각 주입한다. 확인된 시점·대상·범위 내에서만 답하고 추가 지시나 승인을 보내지 않는다. |
| 실제 행동 | 도구 설명 문자열 단위 검사와 별도로 시험 호스트의 새 코디네이터와 기존 지정 세션에서 자연어 질문을 실행한다. 도구 호출 ID·시각·최종 답변을 함께 대조한다. 지침만으로 누락이 반복되면 구조화 출력의 적용 범위를 재검토한다. |
| 자동 알림을 별도로 채택할 때 | 첫 프롬프트가 한 번만 실행되고 즉시 종료해도 원 부모에게 사건당 한 번 전달되는지 확인한다. 재시도·데몬 재시작·권한 대기 뒤 완료·부모가 바쁜 경우·관리 해제·기존 직접 프롬프트 구독과 중복되는 경우를 검증한다. 범위 밖으로 결과를 전달하거나 작업자에게 추가 턴을 만들면 실패다. |

**사용자가 정할 항목** — 응답 시점의 정확성 개선을 우선 채택할지, 사람이 묻지 않아도 결과를 알리는 기능까지 요구할지다. 후자는 수신 범위와 코디네이터 추가 모델 실행 비용을 수반한다. 우선 조회 계약을 적용하고, 능동 통지가 필요할 때 Paseo의 기존 구독을 재사용할 수 있는지부터 검토하는 방안을 추천한다.
